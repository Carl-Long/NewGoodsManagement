# New Goods Management - Development Setup

This guide reproduces the repository skeleton established for **New Goods Management**.

It covers the setup from an empty folder through the initial GitHub push. It intentionally stops before adding business logic, a database, authentication, CORS, or frontend-to-API integration.

## 1. Final technology choices

The repository uses:

- **.NET 10** for the backend API
- **Clean Architecture** for backend project boundaries
- **Next.js** for the frontend
- **TypeScript**
- **Tailwind CSS v4**
- **xUnit** for unit tests
- **npm** as the frontend package manager
- **Git** with a single monorepo
- **VS Code** as the primary editor
- **`.slnx`** solution format

The .NET SDK used while establishing this setup was:

```text
10.0.300
```

The local JavaScript tooling used was:

```text
Node.js 22.20.0
npm 10.9.3
```

Tailwind generated by `create-next-app` was:

```text
Tailwind CSS 4.3.3
```

> This repository deliberately does **not** use `global.json`, so the .NET SDK is not pinned at repository level.

## 14. Configure Clean Architecture project references

The intended dependency direction is:

```text
Domain
  ↑
Application
  ↑
Infrastructure

Application  ← Api
Infrastructure ← Api
```

More explicitly:

```text
Domain
  no project references

Application
  -> Domain

Infrastructure
  -> Application

Api
  -> Application
  -> Infrastructure
```

Add `Application -> Domain`:

```bash
dotnet add \
  src/backend/NewGoodsManagement.Application/NewGoodsManagement.Application.csproj \
  reference \
  src/backend/NewGoodsManagement.Domain/NewGoodsManagement.Domain.csproj
```

Add `Infrastructure -> Application`:

```bash
dotnet add \
  src/backend/NewGoodsManagement.Infrastructure/NewGoodsManagement.Infrastructure.csproj \
  reference \
  src/backend/NewGoodsManagement.Application/NewGoodsManagement.Application.csproj
```

Add `Api -> Application`:

```bash
dotnet add \
  src/backend/NewGoodsManagement.Api/NewGoodsManagement.Api.csproj \
  reference \
  src/backend/NewGoodsManagement.Application/NewGoodsManagement.Application.csproj
```

Add `Api -> Infrastructure`:

```bash
dotnet add \
  src/backend/NewGoodsManagement.Api/NewGoodsManagement.Api.csproj \
  reference \
  src/backend/NewGoodsManagement.Infrastructure/NewGoodsManagement.Infrastructure.csproj
```

Do not add project references merely because they might be useful later. Keep dependencies intentional.

## 17. Resolve the OpenAPI package vulnerability warning

During the original setup, the first build reported `NU1903` because the generated API referenced a version of `Microsoft.OpenApi` with a known high-severity vulnerability.

The issue was resolved by updating the ASP.NET Core OpenAPI package used by the API project:

```bash
dotnet add \
  src/backend/NewGoodsManagement.Api/NewGoodsManagement.Api.csproj \
  package Microsoft.AspNetCore.OpenApi --version 10.0.12
```

Then restore and rebuild:

```bash
dotnet restore
dotnet build NewGoodsManagement.slnx
```

The resulting build should have no vulnerability warning.

> `10.0.12` is the package version used when this setup was established. If intentionally upgrading .NET in the future, update package versions as part of that upgrade rather than blindly retaining this version forever.

# Current architectural decisions

## Backend dependency rules

The initial backend dependency graph is:

```text
NewGoodsManagement.Domain
    ↑
NewGoodsManagement.Application
    ↑
NewGoodsManagement.Infrastructure

NewGoodsManagement.Application
    ↑
NewGoodsManagement.Api

NewGoodsManagement.Infrastructure
    ↑
NewGoodsManagement.Api
```

The key rule is that Domain remains independent of infrastructure/framework concerns.

---

## Tests

The initial repository contains only:

```text
NewGoodsManagement.Domain.Tests
NewGoodsManagement.Application.Tests
```

API integration tests are intentionally deferred until the API contains real endpoints and behaviour worth testing.

---

## CORS

CORS is intentionally **not configured in the initial skeleton**.

It should be added when the first real frontend-to-API integration is implemented. At that point, configure an explicit development policy for the actual frontend origin rather than adding a broad `AllowAnyOrigin()` policy by default.

For example, if the browser frontend runs on `http://localhost:3000`, a future API policy may resemble:

```csharp
builder.Services.AddCors(options =>
{
    options.AddPolicy("Frontend", policy =>
    {
        policy
            .WithOrigins("http://localhost:3000")
            .AllowAnyHeader()
            .AllowAnyMethod();
    });
});
```

followed by:

```csharp
app.UseCors("Frontend");
```

Do not add this until frontend/API communication is actually being introduced.
